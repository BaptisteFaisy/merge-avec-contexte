Un merge check qui regarde le travail, pas seulement le code.

Avant la fusion, il vérifie le ticket Jira lié, les critères d'acceptation, le calendrier des gels, l'état des services et les dépendances — puis il bloque ou avertit en expliquant pourquoi et comment débloquer.

Le problème

Les contrôles ne voient que le code

Build vert, approbations, tâches résolues. Rien ne dit qu'il reste deux critères d'acceptation non cochés, qu'un gel commence dans une heure, ou qu'un incident est ouvert sur le service visé.

Le contexte vit ailleurs

Ces informations sont dans Jira et JSM. Celui qui clique sur « Merge » ne les a pas sous les yeux — alors la fusion part.

Les règles orales ne se tracent pas

« On ne merge pas le vendredi », « pas pendant l'incident » : personne ne peut les vérifier, ni dire qui a dérogé, pourquoi, et jusqu'à quand.

Deux apps Forge, un pont signé

Une app Forge ne peut pas appeler à la fois Bitbucket et Jira : les familles de scopes sont séparées. Le produit est donc coupé en deux, et les deux moitiés se parlent par un web trigger signé HMAC-SHA256 (corps + horodatage + nonce, fenêtre de 5 minutes, anti-rejeu).

Bitbucket

Capteur / Sensor

  • Merge check sur les trois déclencheurs : push, avis d'un relecteur, tentative de fusion
  • Carte de PR et panneau Overview : raisons, marche à suivre, demande de dérogation
  • Réglages de l'espace : jumelage, politique de repli, envoi des chemins
  • Aucune donnée durable, aucune ligne de code source envoyée

Jira

Cerveau / Brain

  • Moteur de règles : portée par dépôt et branche, niveaux, mode observation, dérogations
  • Forge SQL : règles, gels, dérogations, journal, caches — dix tables
  • Écrans : réglages du projet, encart sur le ticket, console de test, journal
  • Agent Rovo et six actions exposées en MCP

Le déroulé d'un contrôle

  1. Bitbucket appelle le Capteur (espace, dépôt, PR, déclencheur).
  2. Le Capteur lit la PR : titre, branches, commits, relecteurs, fichiers modifiés.
  3. Il extrait les clés de tickets : branche, puis titre, puis messages de commit.
  4. Requête signée au Cerveau : clés, dépôt, branche cible, chemins, relecteurs.
  5. Le Cerveau évalue les règles (cache 60 s + base), applique les dérogations, journalise.
  6. Le Capteur rend le verdict et le message ; la carte affiche le détail.

Les treize règles du catalogue

Essayer

Sans rien installer côté Atlassian

git clone https://github.com/BaptisteFaisy/merge-avec-contexte.git
cd merge-avec-contexte
npm install
npm test          # 830 tests
npm run demo      # vrais tickets, app déployée

Sur votre propre site

forge site provision                 # site de démo gratuit
cd cerveau && forge deploy -e production
cd capteur && forge deploy -e production
forge install -e production -p jira  # puis jumelage

Le jumelage se fait par code à usage unique (10 min) dans les réglages, ou par variables d'environnement pour une installation sans navigateur.

Limites, dites franchement

  • Rendre un contrôle obligatoire dans Bitbucket exige l'offre Premium. Sur une offre gratuite, le contrôle s'exécute, affiche exactement le même message et le même verdict, mais informe sans empêcher la fusion.
  • Les merge checks personnalisés ne sont pas proposés aux espaces de travail personnels : il faut un espace d'équipe (gratuit jusqu'à cinq utilisateurs).
  • forge site provision fournit Jira, Confluence, JSM, Rovo et Studio — pas Bitbucket. Le niveau 2 de la démonstration exige donc un espace de travail partagé.
